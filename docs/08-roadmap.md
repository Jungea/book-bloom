# 08. MVP 및 개발 로드맵

> 확인: 2026-11-26
> 상태: 노션 원문 이관. 문서 안의 확정·제안·미정 표기를 그대로 따른다.

## 개발 방향

게임 개발 중심의 에자일 릴리즈. 기존 React.js 독서 관리 서비스는 재활용 후보로 두고, 게임 기능을 작은 단위로 검증한다.

## v0.1 — 나만의 도서관

- [ ] 고정된 방 1개, 벽면 및 바닥 렌더링
- [ ] 책장 1개 배치
- [ ] 개별 책등 렌더링
- [ ] 기존 독서 관리 서비스 연동
- [ ] 최초 읽기 시작 시 재고 1권 생성
- [ ] 최초 완독 시 동일 도서 재고 1권 추가
- [ ] 게임 상태 저장 및 복원

**완료 기준:** 실제 독서 기록으로 책장이 채워지고 재실행해도 유지된다.

제외: 손님, 대여 실행, 재화, 방 확장, 애니메이션. 최초 생성 도서부터 대여 가능하다는 확정 규칙은 v0.3에서 적용한다.

## v0.2 — 움직이는 도서관

손님 스프라이트, 생성 및 퇴장, 상하좌우 이동, 목적지 이동, 책장 앞 대기.

**완료 기준:** 손님이 들어와 책장을 구경하고 나간다.

## v0.3 — 운영하는 도서관

대여 가능 도서 확인, 대여, 대여 중 빈자리, 반납, 반납 도서 정리.

**완료 기준:** 손님이 책을 빌리고 반납하며 사용자가 정리할 수 있다.

전체 시스템 연결 및 안정화.

## 에자일 개발 원칙

- 릴리즈마다 실행 가능한 결과물을 만든다.
- 다음 릴리즈 기능을 미리 구현하지 않는다.
- 임시 에셋 사용을 허용한다.
- 게임 로직 검증 후 그래픽을 개선한다.
- 각 릴리즈에서 저장 및 복원을 검증한다.
- 직접 플레이하고 다음 개발 범위를 결정한다.
- 상세 개발 계획은 바로 다음 릴리즈에 집중한다.

릴리즈별 목표와 순서는 합의된 로드맵이며, 세부 게임 규칙 및 기술 스택, 출시 일정은 별도 확정 전까지 확정하지 않는다.

## 기술 검증 및 구현 단계 (출시 버전과 별도)

| 단계 | 내용 | 완료 기준 |
| --- | --- | --- |

## 서버 비용 최적화 개발 원칙 (확정)

초기 로컬 저장 검증 후 Supabase 무료 플랜으로 서버 연동을 진행한다. 서버 연동 단계에서 Outbox 변경분 일괄 동기화, 중요 이벤트 즉시 동기화 시도, 재연결 재시도, 중복 방지, 단일 기기 운영권 검증을 구현한다. 오프라인 진행은 경과 시간 기반으로 계산하고 서버 상시 실행은 지양한다. 실제 DB 용량·전송량·요청 패턴을 측정하여 동기화 간격 및 이력 보관 정책을 결정한다. 무료 한도 초과 예상 시 최적화 및 유료 전환을 검토한다. 기존 버전별 기능 범위와 기술 개발 순서는 유지한다.

## v0.1 개발 작업 순서 및 개발자 테스트 기능 (확정)

1. 프로젝트 초기 세팅 및 PC 웹 실행
2. 도서관 배경·에셋 배치 및 가로형 4슬롯 검증
3. Android APK 빌드 및 실제 기기 실행
4. 화면 크기·터치 대응
5. 기존 독서관리 코드 선별 재사용
6. 독서관리와 게임 도서 획득 연동
7. 책장 진열 및 로컬 저장 검증
8. v0.1 통합 테스트
v0.1에서는 Supabase 연동을 제외하고 로컬 저장으로 검증한다. 개발 초기부터 버튼으로 임시 도서를 등록·획득할 수 있는 개발자 테스트 모드를 도입하여 독서관리 완성 전에도 게임 기능을 반복 검증한다.

### 테스트 패널 세부 구성 제안

v0.1: 임시 도서 등록, 도서 1권·10권 획득, 책장 채우기, 저장·복원·초기화. 이후 기능 개발과 함께 손님 생성, 대출·반납, 하트·평판, 시설·방, 장르·네임드, 오프라인 시간 경과, 동기화 실패·재시도·중복 방지 테스트를 추가한다. 구체적인 버튼과 UI는 개발 시 결정한다. 테스트 버튼은 실제 게임 로직을 호출하며 테스트 데이터는 실제 데이터와 분리하고 일반 출시 빌드에서 비활성화하는 방향을 적용한다.

## 08-3. 개발 실패 시 대응 원칙 (확정)

PC 실행 오류, Android 빌드 실패, 화면 비율 문제, 기존 기능 오류, 자동 테스트 실패는 신규 기능 개발보다 우선 해결한다. 데이터 저장 오류는 최우선 해결한다. 기술 스택 한계는 대안을 검토하고 사용자 승인 후 변경한다. 개발 범위 증가 시 다음 버전으로 분리하고 기존 코드 재사용 실패 시 해당 기능만 새로 구현한다.

### Git 관리

기능 단위 커밋, 정상 버전 태그, 큰 구조 변경 전 복구 지점 확보, 문제 발생 시 마지막 정상 버전과 비교. AI의 임의 전체 재작성 금지.

### AI 개발 작업

요청 범위 내 수정, 확정 기획 임의 변경 금지, 관련 없는 리팩터링 금지, 신규 라이브러리 도입 전 승인, 수정 파일·테스트 결과·미해결 오류·미구현 사항 보고, 검증 없는 완료 처리 금지.
