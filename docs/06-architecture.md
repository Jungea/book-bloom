# 06. 기술 설계

> 확인: 2026-11-26
> 상태: 노션 원문 이관. 문서 안의 확정·제안·미정 표기를 그대로 따른다.

## 추천 기술 스택 (미확정)

| 영역 | 후보 |
| --- | --- |
| 웹 | Next.js + TypeScript |
| 게임 | Phaser 3 |
| DB 및 인증 | Supabase |
| UI | Tailwind CSS |
| 책 검색 | 알라딘 Open API |
| 배포 | Vercel |

## 구조 제안

React는 독서 기록 UI, Phaser는 현재 방 렌더링 담당. 별도 서버나 마이크로서비스는 초기 제외.

## 검토 필요

API 이용 조건, 비용, 게임 엔진 도입 시점.

## 서비스 플랫폼 및 기술 개발 방향

### 06-3. 시스템 아키텍처

- React: 독서관리, 도서 검색·등록, 독후감, 설정, 통계, HUD, 팝업 및 메뉴.
- Phaser: 배경·시설·책·NPC 렌더링, 이동 표현, 애니메이션, 입력, 카메라.
- 순수 TypeScript Game Core: 재고, NPC 상태 머신, 대출·반납, 하트·평판, 시설, 시간, 오프라인 계산. Phaser와 React에 핵심 규칙을 집중시키지 않는다.
- 저장소 인터페이스 분리: 로컬 저장·복원, 서버 동기화, 처리 시각, 중복 보상 및 충돌 처리. 초기 로컬 검증 후 서버 연동 가능하도록 설계.

### 06-4. 기존 소스 재사용 전략

신규 프로젝트를 구성하고 기존 저장소를 선별 참조한다. 상세 지침: 06-4. 기존 프로젝트 참조 및 코드 재사용 가이드. 실제 파일별 재사용 범위는 코드 검토 후 결정한다.

### 06-5. 게임 렌더링 및 화면 배율

640×360 기본 가로 장면, 4슬롯, 공통 앵커와 접근 좌표. 긴 화면에서는 기본 장면의 가구 크기·비율을 유지하고 배경의 논리 너비를 좌우로 확장한다. Phaser `Scale.FIT` 및 CENTER_BOTH를 사용한다. 1280×720 원본 기준안과 1280×720 논리 대안의 최종 선택은 미확정. 에셋 상세는 05번 참조.

### 06-6. 게임 코어 및 NPC

초기 물리·복잡한 충돌·실시간 길찾기·자유 이동 AI 제외. 공통 통로 및 시설 접근 좌표, 상태 머신 사용. 대출: 입장→책장→선택→데스크→대출→퇴장. 반납: 입장→트레이→반납→퇴장. 트레이 정리는 기존 02번 규칙 유지. 초기 한 종류의 손님과 단순 루프부터 검증하고 이후 확장한다.

### 06-7. 상태 저장 및 오프라인 처리

새로고침, 화면 전환, 방향 변경, 백그라운드, 종료·재실행, 플랫폼 전환 시 상태 유지. 저장 대상: 진행 상태, 손님 ID·행동·위치·목표, 대출·반납, 시설, 도서, 하트·평판, 마지막 처리 시각. 앱 종료 중 Phaser 실행에 의존하지 않고 경과 시간으로 계산한다. 기존 02번 오프라인 규칙 유지: 낮은 효율, 초기 8시간 보상 한도 및 업그레이드, 한도 이후에도 대출·반납 계속. 기본 루프 및 저장 안정화 후 구현.

### 06-8. 서버 연동 및 동기화

계정 연동 이후 서버를 최종 상태 기준으로 사용. PC 웹·Android 동시 접속 및 독서관리 이용을 허용하되 게임 운영은 한 기기에서만 활성화한다. 진행·대출·반납·보상 중복 방지. 운영권 전환, 충돌 처리 및 동기화 세부 방식은 07번 상세 설계에서 확정한다.

### 06-9. Android 빌드 및 배포

Vite 공통 빌드, Capacitor WebView 및 Android Studio. 게임 코드와 핵심 에셋을 앱에 포함하는 방향. APK로 초기 실기기 테스트, 정식 출시 시 서명 AAB를 Google Play Console에 등록. 출시 시점 정책 및 심사 요건 확인. iOS 환경 미구성.

### 06-10. 테스트 및 품질 관리

Vitest 게임 규칙, Playwright 웹 E2E, 타입 검사. 실제 Android에서 APK 설치·가로 전체 화면·배율·입력·NPC 이동·렌더링 성능 검증. 실기기 미검증 기능은 완료로 표시하지 않는다.

### 06-12. 공통 개발 원칙

Asset First, Design First, Fixed Layout, Simple Game Logic, Incremental Development. 명세 외 기능·스택 변경·범위 확대·대규모 리팩토링·신규 의존성은 승인 없이 진행하지 않는다. 규칙 변경 시 테스트·문서 동시 수정. 테스트 및 타입 검사 실패 상태에서 다음 기능 개발 금지. 단계별 정상 버전 Git 기록, 완료 조건 관리.

### 06-13. 기술 검증 및 미확정 사항

Android Phaser 성능·안정성, 최종 논리 해상도·에셋 크기, 독서관리 방향 전환 구현, 기본 진입 화면, 동시 접속 정책, 저장·동기화 방식, 기존 코드 재사용 범위, Google Play 정책. 기술 스택은 실기기 검증 후 최종 확정. 기술 검증 단계는 08번 참조.

06-4. 기존 프로젝트 참조 및 코드 재사용 가이드

## 서버 동기화 방식 (확정)

Supabase를 PC 웹·Android 공통 DB로 유지한다. 게임 연산은 기기에서 실행하며 주요 상태 변화는 로컬에 즉시 저장한다. 서버에는 일정 시간마다 변경 데이터를 묶어 동기화한다. NPC 단순 이동 좌표와 애니메이션은 서버 전송 대상에서 제외한다. 연결 끊김 시 로컬 진행을 유지하고 재연결 시 미동기화 데이터를 반영한다. 기존 단일 기기 게임 운영권 및 중복 방지 정책을 유지한다. 구체적인 동기화 주기와 충돌·운영권 검증 방식은 미확정.

## 무료 플랜 우선 및 서버 사용 최소화 (확정)

Supabase Free를 초기 운영 기준으로 사용한다. 무료 한도 내 운영을 목표로 하되 실제 사용량과 최신 요금제에 따라 유료 전환을 검토한다. Local-first 및 Outbox 기반 변경분 동기화: 주요 상태는 로컬 즉시 저장, 일반 게임 결과는 주기적 일괄 전송, 독서 기록·시설 구매·업그레이드·방 확장·운영 기기 전환 등 중요 이벤트는 즉시 동기화 시도. 변경사항이 없으면 전송하지 않는다. 백그라운드 전환 시 동기화를 시도하되 실패 시 로컬 대기열 유지. PostgreSQL RPC 일괄 처리 및 RLS 적용 방향. NPC 이동·애니메이션은 로컬 처리하고 게임 Realtime 구독 및 서버 상시 시뮬레이션은 기본적으로 사용하지 않는다. 에셋은 앱 및 웹 정적 파일로 제공한다. 무료 한도, 비활성 프로젝트 중지, 백업 제한을 고려한다. 실제 동기화 주기 및 비용은 개발 중 측정한다.

## 개발자 테스트 모드 (확정)

초기부터 개발자 테스트 모드를 도입한다. 독서관리 연동 전에도 버튼으로 임시 도서 등록·획득 및 진열을 반복 검증할 수 있도록 한다. 기능별 테스트 도구를 개발과 함께 확장한다. 실제 게임 로직을 호출하는 테스트 명령, 실제 데이터와 테스트 데이터 분리, 일반 출시 빌드에서 테스트 기능 비활성화를 기본 구현 방향으로 한다. 구체적 패널 UI 및 테스트 명령은 개발 단계에서 결정한다.

## 버전별 검증 완료 기준 (확정)

매 버전마다 자동 테스트, PC 웹 테스트, Android APK 빌드 및 실기기 설치·동작 검증을 수행한다. 오류 수정 및 재검증 후 문서 업데이트, Git 커밋·버전 태그를 진행하고 다음 버전으로 넘어간다. 세부 완료 체크리스트는 08. MVP 및 개발 로드맵을 따른다.

## 개발 실패 대응 및 AI 작업 원칙 (확정)

오류 발생 시 신규 기능보다 기존 정상 상태 복구를 우선하며 데이터 저장 오류는 최우선 처리한다. 기능 단위 Git 커밋, 정상 버전 태그 및 큰 변경 전 복구 지점을 확보한다. AI는 승인 없는 기술 스택·기획·범위 변경, 신규 의존성 도입, 무관한 리팩터링 및 전체 재작성을 하지 않는다. 수정 파일, 테스트 결과, 미해결 오류와 미구현 사항을 보고하고 검증 없이 완료 처리하지 않는다. 세부 대응은 08번 로드맵을 따르며 향후 `AGENTS.md` 및 `CLAUDE.md`에 반영한다.
