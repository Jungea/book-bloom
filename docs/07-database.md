# 07. 데이터베이스 설계

> 확인: 2026-11-26
> 상태: 노션 원문 이관. 문서 안의 확정·제안·미정 표기를 그대로 따른다.

## 데이터 모델 초안

| 테이블 | 역할 |
| --- | --- |
| users | 사용자 |
| books | 도서 정보 |
| reading_logs | 독서 기록 및 독후감 |
| rooms | 방 좌표 및 개방 상태 |
| bookshelves | 책장 위치 및 용량 |
| book_placements | 책장 및 슬롯 배치 |

독서 기록과 게임 배치를 분리하는 방향을 제안한다.

## 미정

ERD, 키와 제약조건, 접근 권한, 재독 및 삭제 정책.

## 플랫폼 공통 데이터 및 동기화 방향

- 계정, 등록 도서, 독서 기록, 독후감, 게임 도서 재고, 시설·책장 배치, 대출·반납, 하트·평판, 해금·성장, 게임 진행 상태를 공통 데이터로 관리한다.
- 손님 ID·행동·위치·목표 및 마지막 처리 시각 저장을 고려한다.
- 초기 로컬 검증 후 Supabase/PostgreSQL 서버 연동을 우선 검토. 계정 연동 이후 서버를 최종 기준으로 사용한다. 동시 접속 중복 처리 방지, 충돌 정책·트랜잭션·동기화 세부 설계는 미확정.

## 07-1. 등록 도서와 게임 도서 자산 (확정)

등록 도서 한 종에 여러 독서 회차 및 개별 게임 도서 자산을 연결하는 1:N 구조를 사용한다. 게임 도서마다 고유 ID를 부여하고 진열 위치, 대출, 반납 상태를 독립적으로 관리한다. 회차별 독후감 및 별점과 보상 지급·회수 이력을 관리한다.

| 논리 테이블명 (초안) | 역할 |
| --- | --- |
| `books` | 등록 도서 기본 정보 |
| `reading_sessions` | 회차별 독서 기록 |
| `reviews` | 독후감 및 별점 |
| `library_books` | 개별 게임 도서 자산 |
| `reading_rewards` | 독서 보상 지급·회수 이력 |

최초 시작 +1권, 최초 완료 +1권, 재독 완료 +1권. 등록·독후감 작성·재독 시작 자체는 도서 수를 늘리지 않는다. 기존 02·03번 보상 및 회수 규칙을 유지한다. 물리 테이블명, 컬럼, 제약조건은 상세 설계에서 확정한다.

## 07-2. 도서관 공간 및 시설 데이터 (확정)

도서관 → 방 → 시설 배치 슬롯 구조로 관리하며 보유 시설은 배치 위치와 독립적으로 관리한다. 방은 고유 ID 및 X·Y 좌표, 방마다 4개의 슬롯을 갖는다. 시설마다 고유 ID, 종류, 레벨, 스킨 및 설치 상태를 관리한다. 시설 이동·교환·보관·재설치 시 ID와 레벨을 유지한다. 책장 내부 진열 위치는 책장 ID에 연결하여 이동 시 도서도 함께 이동하고 업그레이드 시 용량을 확장한다. 기존 02번 시설 배치·재설치·도서 재배치 규칙을 유지한다.

| 논리 테이블명 (초안) | 역할 |
| --- | --- |
| `libraries` | 사용자 도서관 |
| `rooms` | 방 및 좌표 |
| `room_slots` | 방별 시설 배치 슬롯 |
| `facility_types` | 시설 종류 및 기본 성능 정의 |
| `facilities` | 보유 개별 시설 |
| `bookshelf_slots` | 책장 내부 개별 도서 진열 위치 |

물리 테이블명·컬럼·제약조건은 상세 설계에서 확정한다.

## 07-3. 개별 도서 상태 및 대출·반납 데이터 (확정)

개별 도서의 현재 상태와 대출 이력을 분리하고 반납 트레이는 별도 대기열로 관리한다.

- 상태 흐름: 진열(AVAILABLE) → 선택·예약(RESERVED) → 대출(ON_LOAN) → 반납 대기(RETURNED) → 정리 후 진열(AVAILABLE). 진열 공간 부족 시 창고(STORED) 상태이며 대출 불가.
- 손님이 선택하는 순간 예약하여 중복 대출을 방지한다. 예약·대출·반납 대기 중 원래 진열 위치를 유지하며 기존 02번의 책장 제거·재배치 예외를 적용한다.
- 반납 트레이는 용량 제한 없이 정리 대기 순서를 관리한다. 반납 완료 후에도 대출 이력을 보존한다.
- 독서 보상 회수 대상인 대출 도서는 대출을 유지하고 반납 시 제거한다.
| 논리 테이블명 (초안) | 역할 |
| --- | --- |
| `library_books` | 개별 도서 현재 상태 |
| `bookshelf_slots` | 원래 진열 위치 |
| `loans` | 대출 및 반납 이력 |
| `return_queue` | 반납 트레이 및 정리 대기 순서 |
상태 코드, 물리 테이블명, 컬럼 및 중복 방지 제약조건은 상세 설계 시 확정한다.

## 07-4. 손님 및 네임드 데이터 (확정)

일반 손님과 네임드는 공통 방문객 구조를 사용하며 네임드 고유 정보 및 성장 데이터는 별도로 관리한다. 방문마다 방문객 ID를 생성하고 현재 위치, 행동 상태, 목표 시설, 선택 도서를 관리한다. 일반 손님은 퇴장 시 활성 데이터에서 제거하고 필요한 방문 결과만 남긴다. 네임드는 영구 캐릭터 ID, 고유 이름·외형·취향, 발견 여부, 친밀도, 방문 횟수, 요청 진행 상태를 유지한다.

| 논리 테이블명 (초안) | 역할 | 도입 시점 |
| --- | --- | --- |
| `visitor_types` | 일반 손님 유형 정의 | v0.2 |
| `visitors` | 활성 방문객 | v0.2 |
| `visitor_history` | 방문 및 행동 결과 | v0.3 |
| `named_characters` | 네임드 기본 정보 | v0.8 |
| `named_progress` | 발견·친밀도·방문 횟수 | v0.8 |
| `named_requests` | 요청 및 진행 상태 | v0.8 |
| 네임드 관련 테이블은 초기 구현에서 제외한다. 방문 이력 보관 기간과 상세 범위, 물리 테이블명 및 컬럼은 추후 확정한다. |  |  |

## 07-5. 하트·평판·장르 전문성 데이터 (확정)

하트·평판·장르 전문성의 현재 수치와 변동 이력을 분리한다. 하트는 소비형 재화, 평판은 도서관 성장 지표, 전문성은 장르별 성장 지표로 관리한다. 보상 발생 원인을 기록하여 중복 지급을 방지한다. 독서 기록 수정 시 관련 전문성을 재계산하며, 기록 삭제 시 이미 획득한 하트·평판은 유지한다.

| 논리 테이블명 (초안) | 역할 |
| --- | --- |
| `libraries` | 현재 하트 잔액 및 평판 |
| `heart_transactions` | 하트 획득·소비 이력 |
| `reputation_history` | 평판 변동 이력 |
| `genres` | 장르 기본 정보 |
| `genre_mastery` | 장르별 현재 전문성 |
| `genre_mastery_history` | 전문성 증가·회수 이력 |
| 구체적인 보상량, 전문성 최대치, 물리 테이블명·컬럼·중복 방지 제약조건은 추후 확정한다. |  |

## 07-6. 게임 진행 저장 및 오프라인 데이터 (확정)

게임 렌더링과 실제 진행 상태를 분리한다. 주요 상태 변화(도서 획득, 대출·반납, 하트 획득·소비, 시설 구매·이동)는 즉시 저장하고 NPC 단순 이동은 주기적으로 저장한다. 독서관리 화면 전환 및 앱 백그라운드 전환 시 현재 상태를 저장한다. 재접속 시 마지막 처리 시각을 기준으로 경과 시간을 계산하고 상태를 복원한다. 초기 로컬 저장(IndexedDB 우선 검토) 후 Supabase 서버 연동 및 플랫폼 동기화를 적용한다.
기존 오프라인 규칙 유지: 온라인보다 낮은 효율, 초기 8시간 하트·평판 보상 한도, 업그레이드 가능, 한도 이후에도 재고 범위 내 방문·대출·반납 지속.

| 논리 테이블명 (초안) | 역할 |
| --- | --- |
| `game_state` | 게임 진행 및 마지막 처리 시각 |
| `offline_settings` | 오프라인 레벨·효율·보상 시간 한도 |
| `offline_sessions` | 오프라인 진행 결과 |
| `game_events` | 주요 처리 및 중복 방지 기록 |
| `user_settings` | 사용자 환경 설정 |
| 저장 주기, 원자적 처리 방식, 물리 테이블명 및 컬럼은 상세 설계에서 확정한다. |  |

## 07-7. 사용자 계정 및 플랫폼 간 동기화 (확정)

초기에는 로그인 없이 로컬 저장을 사용하고, 서버 연동 이후 공통 계정으로 PC 웹과 Android의 독서 기록 및 도서관 데이터를 공유한다. 서버를 최종 데이터 기준으로 사용한다.

- 동시 접속 정책 B: 두 기기 동시 접속 및 독서관리 이용을 허용하되 게임 진행·조작은 한 기기에서만 활성화한다.
- PC에서 독서 기록을 작성하면서 Android에서 도서관 운영 가능.
- 대출·반납·보상 중복 처리 방지. 독서 활동으로 발생하는 게임 보상도 중복 없이 반영한다.
- 사용자별 데이터 접근을 제한한다.
게임 운영권 전환, 연결 끊김 처리, 동시 독서 기록 수정 충돌, 동기화 및 트랜잭션 구현은 상세 설계에서 확정한다.

- 필요한 테이블만 단계별 생성하고 미구현 콘텐츠의 사전 테이블 생성은 지양한다.

- 중복 보상 및 대출을 방지한다.
- 물리 테이블명, 컬럼, 타입, 제약조건은 해당 기능의 상세 설계 시 확정한다.

## 기획 단계 완료

07-1~07-8의 논리 구조 및 구현 방향 확정. 실제 스키마, ERD 상세, 마이그레이션, 트랜잭션, 동기화 구현은 개발 단계에서 검증 및 확정한다.

## 07-6·07-7 보완: 주기적 서버 동기화 (확정)

로컬 저장과 서버 동기화 주기를 분리한다. 주요 상태 변화는 로컬 즉시 저장하고 Supabase에는 일정 시간마다 변경 데이터를 묶어 반영한다. NPC 단순 이동·애니메이션은 서버 전송 제외. 연결 끊김 시 로컬 진행, 재연결 시 미동기화 데이터 반영. 서버 최종 기준 및 단일 기기 게임 운영 정책 유지. 동기화 간격, 충돌 해결, 재시도 및 운영권 검증 세부 구현은 추후 확정한다.

## 동기화 및 데이터 사용량 최적화 (확정)

Supabase 무료 플랜 우선. 로컬 상태 변경과 Outbox 기록을 일관되게 저장하고 변경 이벤트 고유 ID로 서버 중복 반영을 방지한다. 서버 반영 확인 전까지 대기열을 유지하고 실패 시 재시도한다. 일반 게임 결과는 변경분 일괄 동기화, 독서 기록 및 주요 시설 변경·운영권 전환은 즉시 동기화 시도. 변경분 없으면 전송 생략. 서버 최종 기준과 단일 기기 게임 운영권 유지. 오프라인 경과 시간 계산은 중복 처리 방지 검증을 포함한다. 불필요한 방문·이벤트 이력은 집계 또는 정리하되 보상 중복 방지에 필요한 기록은 유지한다. 표지 이미지는 가능한 URL 참조. 보관 기간, 충돌 처리, 동기화 간격 및 백업 방식은 상세 설계에서 확정한다.
